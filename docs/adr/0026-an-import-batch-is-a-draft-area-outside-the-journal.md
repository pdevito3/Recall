# An Import batch is a draft area outside the journal

An agent writes years of journal text into Recall, the person checks it, and one accept makes it journal (issue #109). The code makes the obvious shape expensive:

- Each insert, update, and delete on `sessions` writes the Sync feed through triggers with no condition (`JournalTriggers.AddSyncFeed`). A draft Session row is in the feed at once.
- A delete of a Session writes a Tombstone that never expires, and `AddSession` then gives 409 for its Client session ID (SES-12). A rejected draft Session would block each later run.
- Revisions are append-only (SES-11), so each edit of a draft Session in the review adds a Revision that stays.
- Every Session read goes through three global query filters. A "draft" filter would be a fourth wall on every reader, now and later.
- The audit log records only the tenant and the owner of a journal row (`AuditModel.RecordOnlyTheOwner`), so an update of a journal row writes no entry.
- `PUT /me/settings` replaces the whole row, and the iOS app sends four fields.
- `JournalRulesTests.no_mcp_tool_or_grpc_service_is_in_a_journal_domain` forbids each MCP tool in a journal domain (SES-15).

Three designs were sketched in parallel, and a separate judge scored them on the isolation of a draft, idempotence, the tool surface, the blast radius, the accept, and the fit of the review. This design takes the parts that scored best. [The imports spec](../specs/imports.md) gives each rule an ID.

1. **A batch and its entries live in their own tables.** `ImportBatch` is a journal-owned root with two states, `Open` and `Accepted`. It owns `ImportEntry` rows, and `ImportDay` rows for a day that the person rejects. These tables have no Sync triggers. So no timeline, Session read, Summary, Cleanup, or Sync feed sees a draft, and no reader of Sessions changes.
2. **The agent and the person write separate layers.** The agent writes Raw, the time from the text, the zone, the position in the source day, the Moods, and the Topics. The person writes the review: a reject of an entry, a reject of a day, and an edit of the words or the time. An agent write never changes the review, so a run again of the agent cannot undo it. At the accept, the edit of the person wins, and the review shows when the agent changed the words after the edit.
3. **One space of Client session IDs for each User.** A unique index on `import_entries(user_id, client_session_id)` keeps an ID in at most one open batch. One loader tells the put and the accept if an ID is a journal Session, has a Tombstone, or is in another open batch. Such an entry is not stored, and its outcome says which. A second run of a whole import after an accept stores only what is new.
4. **The server owns the start time.** An entry carries its date, its position in the source day, and a time only when the text gives one. The start time is that time, or 12:00 plus one minute for each position before it in the source day, timed or not. The position comes from the agent, so a remove leaves a gap and moves no other start time. The server derives it at each read and once at the accept, and it never stores it. A day holds at most 720 entries, so a start time stays on its day. A time in a spring-forward gap moves to the first minute that exists.
5. **The zone of an entry is the zone that the import names,** else the zone of the batch. A Fixed setting does not override it, because the day comes from the date of the source. An unknown zone is refused.
6. **The writes of the agent are an upsert by Client session ID.** `put_import_entries` adds or changes many entries in one call, and the same call again changes nothing. A remove is a separate call. This keeps an agent that splits one day across two calls from removing half of the day.
7. **The accept is one save.** It runs in the shared tenant lock. It makes one Session for each kept entry, with Raw as Revision 1, the Moods and Topics, and `import_batch_id` as the mark. That column has an index and no foreign key, so its migration does not rebuild `sessions` or drop its triggers. It records one `import_batch_accepted` action on the batch with its counts, and it deletes the draft rows, so a reject leaves no Tombstone. The Sync feed carries the new Sessions through the triggers that exist. A stored Summary over their days reads Stale with no new code, because staleness is a fingerprint that a read compares. The accept writes no Person and starts no Cleanup. It sends the version of the batch that its caller read, and an accept of an accepted batch returns its stored result. Each write to a batch moves the version of the batch row, so a put cannot commit between the read and the save of an accept.
8. **With the review on, only a web session of the person accepts,** and only a web session changes the review setting. The agent signs in as the person, so a gate on the route (MCP or REST) does not hold. The gate reads the `client_kind` claim of the auth session, which is `web` only for a browser. With the review off, each caller with journal write accepts, and the audit fact is the same.
9. **The review setting has its own route,** `PUT /me/settings/import-review`, on `UserSetting`. `PUT /me/settings` does not change, so the iOS app needs no change.
10. **A journal MCP tool is for a caller with a journal.** Two new kinds, `ToolAccessKind.JournalRead` and `ToolAccessKind.JournalWrite`, list and permit a tool only for a caller with that access, so a PAT with Read journal access sees only the list tools. SES-15 stays true: a machine agent, a delegated agent, an all-tenants client, a system scope, and a PAT with no journal access have no journal and do not see the tools. Its MCP test changes to "each MCP tool of a journal domain has `JournalRead` or `JournalWrite`", and its ban on a gRPC service stays.
11. **A delete of a User removes each batch** through new lines in `users_purge_journal` for `import_entries`, `import_days`, and `import_batches` (SES-13). Each of the three types has a `user_id`, so the three join `JournalTablesOutsideTheFeed`, and each table gets the owner guard.

## Considered options

- **Batch Sessions as real `sessions` rows with a mark.** The accept is the cheapest here, a change of the mark. It lost because it needs a fourth global filter, a condition on each Sync trigger, the first rebuild of `sessions`, a reject that skips the Tombstone trigger, and a change of `AddSession`. A later migration that copies the nearest `AddSyncFeed("sessions", ...)` line would bring drafts into the feed, and the trigger test checks only names.
- **Many small tools with an entry ID of their own, and the agent computes start times.** The agent then tracks an ID map, the rule of the start time lives in each agent, and an update by the agent can overwrite the edit of the person.
- **One tool that replaces whole days.** It is idempotent and small, but an agent that splits a day across two calls removes the first half with no error.
- **A chained start time** (one minute after the entry before it, whatever its time). A time edit then moves each later entry, and a day can pass midnight. Issue #109 asks for 12:00 plus one minute for each Session before it.
- **The review flag as a field of `PUT /me/settings`.** It changes the replace rule of that route and breaks the iOS save, and any credential of the person could turn the review off.

## Consequences

- An accept is one transaction. A probe on 2026-11-14 saved 10,000 imported Sessions with 1,500 characters of Raw each in 12.5 s, after 5.3 s to build them, with 255 MB of heap. The writer limit is 30 s, so the edge is near 20,000 entries on that machine. The spec proposes a limit of 10,000 kept entries for one accept, and the operator decides it after Phase 2 measures a full accept with its deletes, audit entries, and feed lines. A person splits a larger import into batches, for example by year.
- The import works with a PAT of [ADR 0023](0023-personal-access-tokens-are-auth-sessions.md) that has ReadWrite journal access, with a native session token, and with the session cookie. A PAT with Read journal access can list, and `JournalWriteRule` refuses each write.
- The first entry of a day that is timed or rejected leaves a gap at 12:00. In exchange, a reject, an edit, or a run again never moves another start time.
- Only a web session of the person can accept with the review on. An agent with a PAT cannot, unless a later decision adds a grant for it.
- The SPA and iOS show `startedAt` in the zone of the viewer, not of the Session, so an entry imported at 12:00 in another zone shows another clock time. Its Journaling day stays right.
- The iOS app loads every Session on each list load (`GRDBSyncStore.sessions()`), so thousands of new Sessions at once can slow the list. This is a guess about speed, outside this decision.
- The operator can reverse this decision. The tables, the column, and the index are new, and their migration has a `Down`.
