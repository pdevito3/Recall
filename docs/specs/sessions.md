# Spec: the journal

## 1. Scope

A person opens the phone, dictates, and the entry is captured with no friction. This spec covers the Session and its Revisions, the directory of People, the Corrections, the settings of a User, and the sync feed. Issue #9 gives the reasons. The words of a person are the source of truth, AI never changes them, and no other person can read them.

This spec leaves out Summaries, audio, and each screen. Later units build them. Cleanup is in SES-36 to SES-43. The `CleanupStatus` values and the Revision that the last Cleanup read exist here, so that Cleanup only fills them in.

[ADR 0019](../adr/0019-last-write-wins-for-drafts.md) records Last-write-wins, and [ADR 0020](../adr/0020-journal-rules-in-the-database.md) records the triggers, the delete, and the feed.

## 2. Entities and states

| Entity | Root of | Fields that a user sets | States |
|---|---|---|---|
| `Session` | `RawRevision`, `CleanedRevision` | client session ID, start time, location, Raw, Cleaned, activity, Moods, Topics | None. A Session has no lifecycle. |
| `Person` | | label | None |
| `Correction` | | canonical term, mishearings, hard replace | None |
| `UserSetting` | | time zone, location capture, People proposal review | None |
| `SyncChange` | | None. Triggers write it. | Live, or tombstone |

`CleanupStatus` comes from three stored values, and nothing stores it:

| From | To | Method | Who |
|---|---|---|---|
| NotRun, Clean, Failed | Running | `Session.BeginCleanup` | Cleanup |
| Running | Clean | `Session.CompleteCleanup` | Cleanup |
| Running | Failed | `Session.FailCleanup` | Cleanup |

Each other step is refused, and the Session does not change. A job that stops with no result ends a run with `Session.FailCleanup`.

A `Session` shows `Stale` when its Raw Draft is at a newer Revision than the Revision that the last successful Cleanup read, and no Cleanup runs.

## 3. Rules

| ID | Rule | Enforced by | Backstop |
|---|---|---|---|
| SES-1 | One client session ID of a User makes one Session. A replay of the create returns that Session with 200. | `AddSession` | Unique index on `sessions.user_id, client_session_id` |
| SES-2 | A Session stores an absolute UTC start time that is not in the future. A time from a client names its offset, and a time with no offset gives 400 on each journal route. | `Session.Create`, `InstantWithOffsetConverter` | |
| SES-3 | The Journaling day comes from the start time and the time zone of the User. No column stores it, so a change of the zone moves the Session to its new day. A stored zone that this host does not know also uses UTC, with one warning in the log for each User, and the settings show it with `timeZoneIsKnown` false. | SES-4 | `Stale` has one definition: the Raw Draft is at a newer Revision than the Revision that the last Cleanup read. A save that lost and a hand edit of Cleaned do not make a Session stale. | `Session.CleanupStatusOf` | |
| SES-5 | SES-8 decides first. After that, a save based on the current Draft wins. A save based on an older Draft wins with a save time that is not before the save time of the Draft. A save with a base that names no Draft loses at any save time, and SES-36 says what a base is. A Raw save from a base older than the last chunk loses at any save time, by [REC-6](recordings.md). A win never moves the save time of the Draft back: a win with an older save time keeps the time of the Draft. Two writers that save from an older base can each get `Won`. A word of one writer then leaves the Draft and stays in a Revision, and neither writer gets a signal, because each reply says `Won`. The only trace is a gap in the numbers: a `Won` number above the base plus 1 shows that another Revision came after the base. That Revision lost, or this win overwrote it, and the reply does not say which. | `DraftSlot.Decide`, `Session.SaveRaw` | Primary key on the number of a Revision |
| SES-6 | A save that loses changes no Draft, and its words stay in a Revision. The first save of these words makes the newest Revision, and a replay makes none by SES-8. | `DraftSlot.Decide`, `Session.SaveRaw`, `Session.SaveCleaned` | |
| SES-7 | A claimed time in the future on a Draft save becomes the time of the server, so a fast clock cannot win each later save. | `DraftSave.Of` | |
| SES-8 | A replay sends the same words, the same base, and the same `savedAt`, and it makes no Revision. The first Revision that answers a save gives the answer. A Revision answers when it holds the words of the save and one of these is true: the Draft took it at the base or later, so the reply is `Kept` with its number, or it lost with the same `savedAt`, so the reply is `Lost`. The empty Draft at number 0 has no Revision, so when no Revision answers, it answers an empty save at base 0 with `Kept` and the number 0. A save of the words that the Draft holds comes before this rule: it changes no Draft and no save time, and gives `Unchanged`. So a replay of a save that won or gave `Unchanged` gives `Kept` after later saves or chunks change the Draft. After the Draft moved, a replay of a save that gave `Unchanged` can also give one of two other answers. It can give `Lost`: a save with a base that names no Draft gets `Lost` with a new Revision, and a lost row with the same words and `savedAt` gives `Lost` with no new Revision. It can give `Kept` with another number: the first Draft at the base or later that held the words can have a lower number than the number that `Unchanged` gave. The number of an empty replay at base 0 can also be more than 0, when a Revision that was a Draft holds the empty text. A lost row answers the same words and `savedAt` at any base, also at base 0. So a new save that holds different words, or that lost and comes again after a read, sends a new `savedAt`. | `DraftSlot.Decide`, `SaveRawDraft`, `SaveCleanedDraft` | |
| SES-9 | A Person rename changes the label of each mention in Raw and in Cleaned, and makes a Revision of each text that changes. A save that arrives after the rename with the old label keeps that label, also a save that commits during the rename, because the words of a save are not changed. | `RenamePerson`, `Session.RenamePerson` | |
| SES-10 | On a Session that is not stale, a rename also moves the Revision that the last Cleanup read, so it stays not stale. A stale Session stays stale. A rename does not change the Synopsis. | `Session.RenamePerson` | |
| SES-11 | A Revision is append-only. | `RawRevision`, `CleanedRevision` have no setter | Triggers refuse an update and a delete while the Session stays. `INSERT OR REPLACE` from outside the server fires no trigger, and no code of the server sends it. |
| SES-12 | A delete removes the Session and each of its Revisions, and leaves a tombstone with the two IDs. A replay of its create then gives 409. | `DeleteSession`, `AddSession` | Foreign key cascade, trigger on `sessions` |
| SES-13 | A delete of a User, also through a delete of the tenant, removes the journal of the User and its lines in the feed. | | Trigger on `users` |
| SES-14 | Each journal read has a filter on the owner. The row of another person gives 404, also for an Admin. Each new journal row takes its owner from the caller, and no request names an owner. | `FilterByJournalOwner`, `ApplyJournalOwner` | Test that a handler does not turn the filter off |

| SES-30 | A Cleanup begins only when no Cleanup runs. A Cleanup completes or fails only while it runs. A refused step changes nothing. | `Session.BeginCleanup`, `Session.CompleteCleanup`, `Session.FailCleanup` | |

| SES-34 | A settings save or a metadata save from another version, with the values that the row already holds, does nothing. A retry after a lost reply gets 200 when the first try has finished. A settings retry that overlaps the first try can lose the race on the row and get the 409 of SES-31, and the row holds its values. A metadata retry in that overlap runs again and gets 200. A retry after a newer change holds other values, so it gets the 409 of SES-31 or SES-32 and undoes nothing. A save of the stored values from the current version takes that version and moves it. | SES-35 | The time of a client plays no part in a settings save or a metadata save. A save from the current version applies at any time, and the server ignores a `savedAt` in the body. | SES-36 | A base is 0 or the number of a Revision that was a Draft, and the column `was_draft` holds this fact. A base above the latest number breaks this rule, because a later Revision can take that number. If a client breaks this rule, a replay can answer `Won` and move the Draft: the save first gave `Unchanged`, which writes no row, and its base then became the number of a Draft. The other words stay in a Revision. A `Lost` reply has a null `draftRevision`. After `Lost`, a client reads the Draft, merges once, and saves from the number of the read with a new `savedAt`. The server cannot refuse this number, because it names a Draft, and an older Draft is a base that the time rule of SES-5 decides. | `DraftSlot.Decide`, `SessionMapper.ToSaveResult`, `SaveRawDraft`, `SaveCleanedDraft` | |
