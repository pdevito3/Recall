# Spec: the journal

## 1. Scope

A person opens the phone, dictates, and the entry is captured with no friction. This spec covers the Session and its Revisions, the directory of People, the Corrections, the settings of a User, and the sync feed. Issue #9 gives the reasons. The words of a person are the source of truth, AI never changes them, and no other person can read them.

This spec leaves out Cleanup, Summaries, audio, and each screen. Later units build them. The `CleanupStatus` values and the Revision that the last Cleanup read exist here, so that Cleanup only fills them in.

[ADR 0021](../adr/0021-a-draft-save-wins-only-from-the-current-draft.md) records the save rule of a Draft, and [ADR 0020](../adr/0020-journal-rules-in-the-database.md) records the triggers, the delete, and the feed.

## 2. Entities and states

| Entity | Root of | Fields that a user sets | States |
|---|---|---|---|
| `Session` | `RawRevision`, `CleanedRevision` | client session ID, start time, location, Raw, Cleaned, activity, Moods, Topics | None. A Session has no lifecycle. |
| `Person` | | label | None |
| `Correction` | | canonical term, mishearings, hard replace | None |
| `UserSetting` | | time zone, location capture, People proposal review | None |
| `SyncChange` | | None. Triggers write it. | Live, or tombstone |

`CleanupStatus` comes from three stored values, and nothing stores it:

| From | To | Method | Who |
|---|---|---|---|
| NotRun, Clean, Failed | Running | `Session.BeginCleanup` | Cleanup |
| Running | Clean | `Session.CompleteCleanup` | Cleanup |
| Running | Failed | `Session.FailCleanup` | Cleanup |

Each other step is refused, and the Session does not change. A job that stops with no result ends a run with `Session.FailCleanup`.

A `Session` shows `Stale` when its Raw Draft is at a newer Revision than the Revision that the last successful Cleanup read, and no Cleanup runs.

## 3. Rules

| ID | Rule | Enforced by | Backstop |
|---|---|---|---|
| SES-1 | One client session ID of a User makes one Session. A replay of the create returns that Session with 200. | `AddSession` | Unique index on `sessions.user_id, client_session_id` |
| SES-2 | A Session stores an absolute UTC start time that is not in the future. A time from a client names its offset, and a time with no offset gives 400 on each journal route. | `Session.Create`, `InstantWithOffsetConverter` | |
| SES-3 | The Journaling day comes from the start time and the time zone of the User. No column stores it, so a change of the zone moves the Session to its new day. A zone change does not put the Sessions in the sync feed, so a client derives the day from the start time and the zone of the settings row. A User with no zone uses UTC. A stored zone that this host does not know also uses UTC, with one warning in the log for each User, and the settings show it with `timeZoneIsKnown` false. A change can send the stored zone back, and any other unknown zone gives 422. | `SessionMapper.ToSessionDto`, `GetSessionPage`, `UserSetting.ZoneOf`, `UserSettingQueries.JournalZoneOf`, `UserSetting.Change` | |
| SES-4 | `Stale` has one definition: the Raw Draft is at a newer Revision than the Revision that the last Cleanup read. A save that lost and a hand edit of Cleaned do not make a Session stale. | `Session.CleanupStatusOf` | |
| SES-5 | SES-8 decides first. After that, a save wins only when its base is the number of the current Draft. A save from any other base gets `Lost`, at any `savedAt`. So of two saves from one base, the first to arrive wins, and the other gets `Lost`. A chunk ([REC-6](recordings.md)), a rename (SES-9), and a Cleanup each move the number, so a save from before them gets `Lost`. So no save replaces words that its client did not hold. | `DraftSlot.Decide`, `Session.SaveRaw`, `Session.SaveCleaned` | Primary key on the number of a Revision |
| SES-6 | A save that loses changes no Draft, and its words stay in a Revision. The first save of these words makes the newest Revision, and a replay makes none by SES-8. | `DraftSlot.Decide`, `Session.SaveRaw`, `Session.SaveCleaned` | |
| SES-7 | `savedAt` decides no save. With the words, it is the identity of a save for SES-8. It is also the time that a Revision shows and that the Draft shows after a win. The server stores the time that the client sent, in UTC, so a fast clock can show a time in the future, and a win from a slow clock moves the time of the Draft back. | `DraftSave.Of`, `DraftSlot.Decide` | |
| SES-8 | A replay sends the same words and the same `savedAt`, and it gets the answer of its first try. The first Revision with these words and this `savedAt` gives the answer: a Revision that won gives `Kept` with its number, and a Revision that lost gives `Lost`. Neither makes a Revision, and the column `was_draft` holds which of the two it is. This rule comes first, so a replay of a win gives `Kept` also when the Draft still holds the words, and a replay of a loss gives `Lost` also when the Draft now holds the words. After this rule, a save of the words that the Draft holds changes no Draft and no save time, and gives `Unchanged`. `Unchanged` writes no Revision, so no Revision answers its replay. While the Draft holds the words, the replay gives `Unchanged` again. After the Draft moves, SES-5 decides the replay as a new save, so from an older base it gets `Lost` with a new Revision, and each later replay gets `Lost` from that Revision. So a new save that holds different words, or that lost and comes again after a read, sends a new `savedAt`. | `DraftSlot.Decide`, `SaveRawDraft`, `SaveCleanedDraft` | |
| SES-9 | A Person rename changes the label of each mention in Raw and in Cleaned, and makes a Revision of each text that changes. This moves the number of that Draft, so a save from before the rename gets `Lost`, and its words stay in a Revision with the old label. A rename that changes no text of a Draft does not move its number. A save that wins with the old label keeps that label, because the words of a save are not changed. This can be a save from the number after the rename, or a save that adds the first mention while the rename runs. | `RenamePerson`, `Session.RenamePerson` | |
| SES-10 | On a Session that is not stale, a rename also moves the Revision that the last Cleanup read, so it stays not stale. A stale Session stays stale. A rename does not change the Synopsis. | `Session.RenamePerson` | |
| SES-11 | A Revision is append-only. | `RawRevision`, `CleanedRevision` have no setter | Triggers refuse an update and a delete while the Session stays. `INSERT OR REPLACE` from outside the server fires no trigger, and no code of the server sends it. |
| SES-12 | A delete removes the Session and each of its Revisions, and leaves a tombstone with the two IDs. A replay of its create then gives 409. | `DeleteSession`, `AddSession` | Foreign key cascade, trigger on `sessions` |
| SES-13 | A delete of a User, also through a delete of the tenant, removes the journal of the User and its lines in the feed. | | Trigger on `users` |
| SES-14 | Each journal read has a filter on the owner. The row of another person gives 404, also for an Admin. Each new journal row takes its owner from the caller, and no request names an owner. | `FilterByJournalOwner`, `ApplyJournalOwner` | Test that a handler does not turn the filter off |
| SES-15 | A machine agent, an all-tenants client, a delegated agent, and a system scope have no journal. They get 403 where a route has no ID, and 404 where it has one. | `CallerIdentity.JournalOwnerId`, `RequireJournalOwner` | |
| SES-16 | A pull from a cursor gives each change once and in order, also when two saves have the same timestamp. A save during the read comes in the next page. | `GetSyncChangePage` | Triggers with an `AUTOINCREMENT` sequence |
| SES-17 | A cursor ahead of the newest change of the User gives 422, and the feed has no other 422. A cursor or a page size that is not valid gives 400. | `GetSyncChangePage`, `SyncCursor.Parse` | |
| SES-18 | A location with capture off, partial, or not on the globe is not stored. | `CapturedLocation.Admit` | |
| SES-19 | No journal text reaches a log, a span, or an audit value. | `AuditModel`, `DraftSave`, each handler | Test with a marker through each write route |
| SES-20 | Cleanup does not change Raw. A successful Cleanup replaces Cleaned and keeps the copy as a Revision, and a hand edit after it marks Cleaned. | `Session.CompleteCleanup`, `Session.SaveCleaned` | |
| SES-21 | The Moods and the Topics of a Session are trimmed, in one spelling, and have no duplicate. A change by the User keeps the AI Topics, except a Topic that the change also holds. Two Topics match when they are the same after a trim, with case ignored. The Topic is then the Topic of the User, in the spelling of the User, so a later removal by the User removes it. A write of AI Topics must not add a Topic that the User holds. A metadata save replaces the Activity, the Moods, and the User Topics, and SES-32 to SES-35 decide if it applies. | `SessionMetadata.Of`, `Session.SetMetadata` | |
| SES-22 | The People of a Session are the Persons that its Raw and its Cleaned mention, and no other list. A mention with the Person ID of another person stays in the list of the owner of the Session, and it reveals no label. | `Session.RefreshFromDrafts` | |
| SES-23 | The preview has the first 200 characters of the plain text of Raw, and a rename or a save changes it. | `Session.RefreshFromDrafts` | |
| SES-24 | The label of a Person is trimmed and not blank. | `Person.Create`, `Person.Rename` | |
| SES-25 | A Correction has a trimmed term that is not blank. Its mishearings are trimmed, have no duplicate, and do not hold the term. | `Correction.Create`, `Correction.Update` | |
| SES-26 | Location capture is off until the User turns it on. A settings save replaces the whole row, and SES-31 and SES-33 to SES-35 decide if it applies. | `UserSetting.DefaultsFor`, `UserSetting.Change` | Unique index on `user_settings.user_id` |
| SES-27 | After a delete of a Session, a Correction, a User, or a tenant with no long reader, its words are not in the database file or in the WAL. A kill between the commit of the delete and the truncate can leave the words in the WAL, and each start of the server truncates the WAL before it takes a request. A reader that holds on past the wait of the truncate can keep the old pages, and at a start the server then logs a Warning. They stay in the database file until a later checkpoint passes the delete, and in the WAL until later writes overwrite them, a later truncate, a cut to the size limit, or the close of the last connection. | `PRAGMA secure_delete`, `WalScrub`, `MigrationHostedService`, `DeleteSession`, `DeleteCorrection`, `DeleteUser`, `DeleteTenant` | |
| SES-28 | A timeline read that follows its cursors gives no row twice and misses no row that existed at its first page, also when two Sessions have the same start time. A Session that arrives between two pages and sorts after the cursor comes in a later page. A Session that sorts ahead of the cursor, with a newer start, or with the same start and a later ID, which each new Session has, comes in no later page. A read from the start or the sync feed gives it. | `GetSessionPage`, `SessionCursor` | Index on `sessions.user_id, started_at, id` |
| SES-29 | Each text that JSON and the database can hold saves and comes back exactly, also a text that is not a good ProseMirror document. Its preview is the text, it mentions no Person, and a rename does not stop on it. A text with a raw NUL gives 422, and a raw lone surrogate in the body gives 400. A ProseMirror text that holds the escape of a lone surrogate saves and comes back. A rename keeps that text as it is, with the old label, because the server cannot write it again with no change to the words, and the rename goes on with the other texts. A label that is itself the lone surrogate does get the new label. | `ProseMirrorNode.TryRead`, `Session.PreviewOf` | |
| SES-30 | A Cleanup begins only when no Cleanup runs. A Cleanup completes or fails only while it runs. A refused step changes nothing. | `Session.BeginCleanup`, `Session.CompleteCleanup`, `Session.FailCleanup` | |
| SES-31 | A settings save sends the `version` of the row that the client read. The read of a User with no row gives version 0, and a save from 0 makes the row. A save from another version gets 409 with the type `urn:recall:problem:stale-version` and a reason in `errors.version`, and it changes nothing. So a stale client cannot turn location capture on again, and the next Session stores no location. | `UserSetting.Change` | `version` as a concurrency token, unique index on `user_settings.user_id` |
| SES-32 | A metadata save sends the `metadataVersion` of the Session that the client read. Only a metadata change that applies moves it, so a save of words does not refuse a metadata save. A save from another version gets 409 with the type `urn:recall:problem:stale-version` and a reason in `errors.metadataVersion`. The Activity, the Moods, the Topics, and the words stay. | `Session.SetMetadata`, `StaleMetadataVersionException` | `version` of the Session row: a save that loses a race with a Draft save runs again |
| SES-33 | A settings save with no `version` or a metadata save with no `metadataVersion` gives 400 and changes nothing. So a client that sends the older body fails with a reason, and it overwrites no value. A Draft save asks for neither, so this refusal stops no words. | `required` on `UserSettingChangeDto.Version` and `SessionMetadataChangeDto.MetadataVersion` | |
| SES-34 | A settings save or a metadata save from another version, with the values that the row already holds, does nothing. The reply is 200 with the stored row, the version does not move, and the zone has no check. A save that does nothing writes nothing, so it makes no row for a User with no row. A retry after a lost reply gets 200 when the first try has finished. A settings retry that overlaps the first try can lose the race on the row and get the 409 of SES-31, and the row holds its values. A metadata retry in that overlap runs again and gets 200. A retry after a newer change holds other values, so it gets the 409 of SES-31 or SES-32 and undoes nothing. A save of the stored values from the current version takes that version and moves it. So two saves from one read with different values cannot both change the row, in any order or overlap. | `UserSetting.Change`, `ChangeUserSetting`, `Session.SetMetadata` | `version` as a concurrency token |
| SES-35 | The time of a client plays no part in a settings save or a metadata save. A save from the current version applies at any time, and the server ignores a `savedAt` in the body. So a 200 means that the row holds the values that the client sent, after the rules of SES-21, and a 409 means that nothing changed. | `UserSetting.Change`, `Session.SetMetadata` | |
| SES-36 | A base is the number of a Draft whose text the client holds: 0 for the empty Draft, or a number that a read of the Session or a `Won`, `Unchanged`, or `Kept` reply gave it. Only the number of the current Draft wins, so an old number cannot replace newer words. A Revision that lost never becomes the Draft, so its number, which `latestRevision` can be, gets `Lost`. A client must not guess a number above the latest number. A later Draft can take that number, and a save from it then wins over words that the client did not read. A `Lost` reply has a null `draftRevision`. After `Lost`, a client reads the Draft, merges once, and saves from the number of the read with a new `savedAt`. The steps that stop a repeat of text are in [iOS API changes](../ios-api-changes.md#the-base-of-a-draft-save). `Kept` gives the number at which the Draft took these words, and a client adds nothing, because the Draft already took them. | `DraftSlot.Decide`, `SessionMapper.ToSaveResult` | |
